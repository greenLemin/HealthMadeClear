### Layering Rules (One-Way Dependency Direction)

```
app/[locale] (server components) ──┐
                                   ├──→ lib/dashboard/* ──→ lib/supabase/server
                                   │
app/[locale] (client components) ──┤
                                   ├──→ hooks/* ──→ lib/* (client-safe only)
                                   │
components/* ──→ components/ui/* ──┘
                └──→ lib/markdown/* (pure utilities)

FORBIDDEN:
- Client components importing from lib/supabase/server
- Hooks importing from lib/dashboard/* (server data-access) — DT-003 fix
- Components importing types from other components — T-001, T-008 fix
- Sibling content-domain parsers reaching across (lessons → paths) — DT-005 fix
```

### Naming Conventions (Codified)

| File Type                      | Convention                      | Example                             |
| ------------------------------ | ------------------------------- | ----------------------------------- |
| React components               | PascalCase                      | `Header.tsx`, `DashboardClient.tsx` |
| Page / route / loading / error | kebab-case (Next.js convention) | `page.tsx`, `loading.tsx`           |
| Utilities, hooks, libs         | camelCase                       | `logger.ts`, `useProgress.ts`       |
| Type definitions               | camelCase                       | `src/types/dashboard.ts`            |
| Tests                          | colocated `*.test.ts(x)`        | `Header.test.tsx`                   |

**Enforcement:** Add `eslint-plugin-check-file` (already in next config) and document rule in `AGENTS.md`.

### Export Style Rules (Codified)

- **Pages / layouts / loading / error / route handlers:** `export default` (Next.js convention)
- **React components:** `export default function ComponentName()` — imported as `import ComponentName from "@/components/..."`
- **Utilities, hooks, types, constants:** Named exports — `export function X()`, `export type Y`
- **Component prop types:** Defined as `type ComponentNameProps = {...}` inline at top of component file (not exported) — exception: shared prop types go in `src/types/`

### Where Every Category of Code Lives

| Category              | Home                                        | Rule                                                                                  |
| --------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------- |
| Cross-domain types    | `src/types/`                                | All types here; feature-local types only if used by 1 feature                         |
| React components      | `src/components/`                           | Shared UI primitives in `src/components/ui/`; feature components colocated with route |
| Hooks                 | `src/hooks/`                                | All custom hooks; one hook per file unless tightly coupled                            |
| Server-only utilities | `src/lib/` (server-safe)                    | Never imported by client components                                                   |
| Client-safe utilities | `src/lib/` (no server-only deps)            | OK to import from client components                                                   |
| Supabase queries      | `src/lib/<domain>/*.ts`                     | One module per table; no direct Supabase calls from components                        |
| i18n messages         | `src/messages/{en,es}.json`                 | All user-facing strings here                                                          |
| Content bundles       | `src/data/*`                                | Auto-generated; do not edit                                                           |
| Test utilities        | `src/test-utils.tsx` (or `src/test-utils/`) | Shared test setup                                                                     |
| Test files            | Colocated `*.test.ts(x)`                    | Never `__tests__/`                                                                    |

## Safety Strategy

### Characterization Tests (BEFORE Risky Moves)

For each high-risk task (WS-3.3, WS-4.2, WS-4.3, WS-6.1, WS-8.1), the agent must first:

1. **Run existing tests** for the affected scope to confirm green baseline
2. **Write a snapshot test** (or expand an existing one) that captures the rendered output of the component before the refactor. For `progress-client.tsx` (WS-4.2), this means: render the component with mock props → snapshot the HTML → refactor → re-snapshot → diff must be empty.
3. **Run Playwright e2e for the affected route** before and after the refactor. For dashboard work: `npx playwright test dashboard`. For auth work: `npx playwright test auth`.

### Incremental-Move Pattern

Every task follows: **move → verify → commit → next**. The agent must:

1. Make the smallest possible change that achieves the task's acceptance criteria
2. Run the task's verification commands (typically `npm run typecheck && npx vitest run`)
3. If green, commit with a conventional-commit message: `refactor(<scope>): <description>`
4. If red, fix the issue and re-verify before committing

### Rollback Approach

Each task is an atomic commit. If a task fails verification and cannot be fixed within the same workstream, the coordinator:

1. Runs `git revert <commit-sha>` to undo the task
2. Logs the revert in `DESPAGHETTI_LOG.md`
3. Adds the task to a follow-up list (still must be completed in this mission, but with a revised approach)

For workstreams that touch many files (WS-4, WS-13), the agent should make multiple smaller commits within the workstream, each verifiable independently.
