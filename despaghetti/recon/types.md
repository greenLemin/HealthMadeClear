# Types Recon

## Method

- Read every file in `src/types/` (glossary.ts, article.ts, content.ts, lesson.ts, database.ts, global.d.ts, learningPath.ts, quiz.ts) and the codemap.md in `src/types/`.
- Read `src/app/[locale]/dashboard/types.ts` and `src/app/[locale]/tools/visit-planner/types.ts` (types defined OUTSIDE `src/types/`).
- Read every file in `src/lib/dashboard/` (progress.ts, learningPaths.ts, activity.ts, achievements.ts, recommendations.ts, quizzes.ts, dailyLog.ts, profile.ts, utils.ts, index.ts) to find inline anonymous return types.
- Read `src/app/[locale]/dashboard/progress/progress-client.tsx` (re-declares `Summary` inline).
- Read `src/components/dashboard/AchievementCard.tsx` (exports its own `AchievementItem`).
- Read `src/components/mdx/InlineGlossaryTerm.tsx` (exports `GlossaryTermSummary`).
- Read `src/lib/notifications.ts`, `src/lib/progressExport.ts`, `src/hooks/useProgress.ts`, `src/data/searchIndex.en.ts`, `src/data/searchIndex.es.ts` to inventory duplicates and divergences.
- Ran `rg "^(export )?(interface|type) \w+" -g "*.ts" -g "*.tsx" src | sort` to inventory all named type definitions in `src/`.
- Ran `rg ": any\b|<any>|as any\b" -g "*.ts" -g "*.tsx" src` to count `any` usage (160 hits total; 4 non-test; 156 in `.test.` files).
- Ran `rg "import.*\bX\b"` for each candidate type to map consumers and detect cross-source imports.
- Confirmed exact-shape duplicates by reading both definitions and diffing field-by-field.

## Findings

### T-001: `AchievementItem` duplicated exactly in two files

- **Category:** duplicate-type
- **Severity:** P1
- **Files:** `src/components/dashboard/AchievementCard.tsx:6`, `src/app/[locale]/dashboard/types.ts:32`
- **Description:** `AchievementCard.tsx:6-13` declares `export type AchievementItem = { id; title; description; icon; earned; earnedAt: string | null }`. `dashboard/types.ts:32-39` declares the identical `export type AchievementItem` with the same seven fields in the same order. Two consumers import different sources: `src/app/[locale]/dashboard/achievements/achievements-client.tsx:9` imports `AchievementItem` from `@/components/dashboard/AchievementCard`, while `src/app/[locale]/dashboard/components/EarnedAchievements.tsx:5` imports it from `../types`. Both copies are alive. If a field is added or renamed on one side, the other consumer will silently break or be re-typed.
- **Suggested remedy:** Delete the copy in `AchievementCard.tsx`. Have the component import `AchievementItem` from `src/types/dashboard.ts` (move dashboard types to `src/types/`, see T-005). Re-export from `AchievementCard.tsx` only if a back-compat barrel is needed.

### T-002: `Notification` interface duplicated exactly in two files

- **Category:** duplicate-type
- **Severity:** P1
- **Files:** `src/types/database.ts:53`, `src/lib/notifications.ts:78`
- **Description:** `database.ts:53-61` declares `export interface Notification { id; user_id; type; title; body; read; created_at }`. `notifications.ts:78-86` declares the identical `export interface Notification` with the same seven fields. The database-side type is the `Database["public"]["Tables"]["notifications"]["Row"]` source-of-truth (via `database.ts:97-99`), but `notifications.ts` redefines the same shape from scratch and uses it in its public function signatures (`getNotifications`, `markAsRead`, `markAllAsRead`, `getUnreadCount`). Drift risk: if a column is added to the Supabase schema and `database.ts` is regenerated, `notifications.ts`'s copy will be silently out of sync.
- **Suggested remedy:** Remove the `Notification` interface from `src/lib/notifications.ts`. Import `Database["public"]["Tables"]["notifications"]["Row"]` (or a named `Notification` re-export from `src/types/database.ts`) and use it in the function signatures. Keep `NotificationInput` (the insert-shape sibling) in `notifications.ts` since it is a separate, narrower type.

### T-003: `SearchEntry` + `SearchEntryType` duplicated exactly in two locale files

- **Category:** duplicate-type
- **Severity:** P2
- **Files:** `src/data/searchIndex.en.ts:4-15`, `src/data/searchIndex.es.ts:4-15`
- **Description:** Both files open with:
  ```ts
  export type SearchEntryType = "lesson" | "article" | "glossary" | "path" | "tool";
  export interface SearchEntry {
    id;
    type;
    title;
    description;
    category;
    categoryId;
    content;
    url;
  }
  ```
  Two identical exports in two locale files. Both are consumed by `src/components/SearchDialog.tsx:1` which imports `SearchEntry` from `@/data/searchIndex.en` (locale-bound). If the schema of `SearchEntry` ever needs to evolve, both files must be edited in lockstep; nothing enforces this. The file header says "Auto-generated by scripts/build-search-index.ts — do not edit by hand," so the duplication is a build-pipeline artifact, not an accident — but the type exports still ought to live in one place.
- **Suggested remedy:** Move `SearchEntry` and `SearchEntryType` to `src/types/search.ts`. Have both `searchIndex.en.ts` and `searchIndex.es.ts` import the type from `src/types/search.ts` and only export the data array. Update `SearchDialog.tsx` to import the type from `src/types/search.ts` instead of the locale-specific data file.

### T-004: `Summary` duplicated in dashboard types and progress client

- **Category:** duplicate-type
- **Severity:** P2
- **Files:** `src/app/[locale]/dashboard/types.ts:3`, `src/app/[locale]/dashboard/progress/progress-client.tsx:13`
- **Description:** `dashboard/types.ts:3-12` declares `export type Summary = { totalLessonsCompleted; totalLessonsAvailable; totalQuizzesPassed; totalQuizzesAttempted; averageQuizScore; totalTimeSpentMinutes; currentStreak; longestStreak }`. `progress-client.tsx:13-22` re-declares the identical `type Summary = {...}` inline (not exported) before using it as the shape of `ProgressClientProps.summary`. The client component has no import path back to `dashboard/types.ts` and instead redefines the shape by hand. Any change to the canonical `Summary` (e.g., adding `totalLearningPaths`) will not propagate to the progress client; TypeScript will silently accept the narrower shape at the page→client boundary.
- **Suggested remedy:** Move `Summary` to `src/types/dashboard.ts` (see T-005). Import it in both `dashboard/types.ts` (or remove the latter) and `progress-client.tsx`. Delete the inline redeclaration in the client.

### T-005: Dashboard domain types live in a feature folder, not `src/types/`

- **Category:** wrong-location
- **Severity:** P1
- **Files:** `src/app/[locale]/dashboard/types.ts:1-58`
- **Description:** `src/app/[locale]/dashboard/types.ts` defines six exported domain types — `Summary`, `LearningPathEntry`, `ActivityItem`, `AchievementItem`, `RecommendedLesson`, `DashboardClientProps` — that describe data flowing from `src/lib/dashboard/*` server functions to client components. They are not React-component-prop local types; they are cross-layer contracts consumed by `DashboardClient.tsx`, `DashboardHeader.tsx`, `DashboardStats.tsx`, `LearningPaths.tsx`, `RecentActivity.tsx`, `RecommendedNext.tsx`, `EarnedAchievements.tsx`, and `achievements-client.tsx`. The `src/types/codemap.md` declares `src/types/` to be the home for "TypeScript type definitions for all domain entities and database schema," but dashboard types are absent from `src/types/`. Result: the canonical-type directory is incomplete, and a contributor reading `src/types/` has no signal that dashboard types exist elsewhere.
- **Suggested remedy:** Move the six exported types from `src/app/[locale]/dashboard/types.ts` to a new file `src/types/dashboard.ts`. Have `dashboard/types.ts` either be deleted (preferred — re-import from `@/types/dashboard`) or be turned into a re-export barrel (`export type * from "@/types/dashboard";`). Update all dashboard components and `achievements-client.tsx` to import from `@/types/dashboard`. Also delete the `AchievementItem` redefinition in `AchievementCard.tsx` (T-001) as part of the move.

### T-006: Visit-planner types live in a feature folder, not `src/types/`

- **Category:** wrong-location
- **Severity:** P2
- **Files:** `src/app/[locale]/tools/visit-planner/types.ts:1-13`
- **Description:** `src/app/[locale]/tools/visit-planner/types.ts` defines four exported types — `VisitTypeKey`, `StepValue`, `CustomQuestion`, `PlannerState` — plus the `VISIT_TYPE_KEYS` const. They are consumed by `useVisitPlanner.ts`, `VisitPlannerClient.tsx`, and the three Step components. These are not component-prop types; they are domain/state types for the visit-planner feature. `src/types/` is supposed to be the canonical home but does not include these. Same anti-pattern as T-005 but lower-severity because the feature is self-contained.
- **Suggested remedy:** Move the four exported types (and arguably `VISIT_TYPE_KEYS`) to `src/types/visitPlanner.ts`. Update imports in `useVisitPlanner.ts`, `VisitPlannerClient.tsx`, and the Step components to use `@/types/visitPlanner`. Either delete the local `types.ts` or convert it to a re-export barrel.

### T-007: `src/lib/dashboard/*` functions return inline anonymous types that duplicate `dashboard/types.ts` shapes

- **Category:** divergent-type
- **Severity:** P1
- **Files:** `src/lib/dashboard/progress.ts:6-19`, `src/lib/dashboard/learningPaths.ts:13-21`, `src/lib/dashboard/activity.ts:11-19`, `src/lib/dashboard/achievements.ts:11-18`, `src/lib/dashboard/recommendations.ts:11-18`
- **Description:** Each of these lib functions declares its return type inline as an anonymous object literal:
  - `progress.ts:6-19` — `Promise<{ totalLessonsCompleted; totalLessonsAvailable; totalQuizzesPassed; totalQuizzesAttempted; averageQuizScore; totalTimeSpentMinutes; currentStreak; longestStreak }>` ≡ `Summary` in `dashboard/types.ts:3-12`.
  - `learningPaths.ts:13-21` — `Promise<Array<{ path: LearningPath; completedLessonIds: string[]; nextLesson: { id: string; title: string; duration: string } | null; progressPercentage: number; isComplete: boolean }>>` ≡ `LearningPathEntry[]` in `dashboard/types.ts:14-20`.
  - `activity.ts:11-19` — `Promise<Array<{ type: "lesson" | "quiz"; lessonId?; quizId?; title; completedAt; score?; passed? }>>` ≡ `ActivityItem[]` in `dashboard/types.ts:22-30`.
  - `achievements.ts:11-18` — `Promise<Array<{ id; title; description; icon; earned; earnedAt: string | null }>>` ≡ `AchievementItem[]` in `dashboard/types.ts:32-39` (and in `AchievementCard.tsx:6-13`).
  - `recommendations.ts:11-18` — `Promise<{ id; title; description; duration; level; pathTitle? } | null>` ≡ `RecommendedLesson | null` in `dashboard/types.ts:41-48`.

  The lib layer does not import the dashboard types. The shapes are duplicated by hand. The server functions in `src/app/[locale]/dashboard/page.tsx` (and `progress/page.tsx`, `achievements/page.tsx`) call these libs and pass results into client components typed via `dashboard/types.ts`. TypeScript structural typing means the inline shape and the named type happen to be assignable today, but a one-field change on either side will silently desync. The lib→page→client contract is effectively undocumented.

- **Suggested remedy:** Have each lib function import its corresponding type from `src/types/dashboard.ts` (after T-005) and use it as the return type. Example: `getUserLearningPaths(...): Promise<LearningPathEntry[]>`. Delete the inline anonymous shapes. This makes the lib→client contract explicit and lets TypeScript catch drift.

### T-008: `AchievementItem` is consumed from two different import paths

- **Category:** type-leak
- **Severity:** P1
- **Files:** `src/app/[locale]/dashboard/achievements/achievements-client.tsx:9`, `src/app/[locale]/dashboard/components/EarnedAchievements.tsx:5`, `src/components/dashboard/AchievementCard.tsx:6`, `src/app/[locale]/dashboard/types.ts:32`
- **Description:** Follow-on to T-001. There are two live `AchievementItem` types and two import paths in active use:
  - `achievements-client.tsx:9` imports `AchievementItem` from `@/components/dashboard/AchievementCard` (the component-file copy).
  - `EarnedAchievements.tsx:5` imports `AchievementItem` from `../types` (the dashboard-types copy).
    Both types are structurally identical, so the code compiles, but consumers do not know they share a type. A field added to the `AchievementCard` copy will not be visible to `EarnedAchievements` (which uses the `dashboard/types.ts` copy), and vice versa. The component file `AchievementCard.tsx` is effectively acting as a types-barrel, which is a type-leak from a presentational component into the type system.
- **Suggested remedy:** Single-source `AchievementItem` in `src/types/dashboard.ts`. Both `AchievementCard.tsx` and `EarnedAchievements.tsx` import from `@/types/dashboard`. Remove the `export type AchievementItem` from `AchievementCard.tsx:6-13`.

### T-009: `GlossaryTermSummary` is a domain-shaped type living inside a component file

- **Category:** wrong-location
- **Severity:** P2
- **Files:** `src/components/mdx/InlineGlossaryTerm.tsx:12`
- **Description:** `InlineGlossaryTerm.tsx:12-16` declares `export interface GlossaryTermSummary { id: string; term: string; definition: string }` with the doc-comment "The minimal shape of a glossary term needed to render the popover." It is consumed by the same file (in `InlineGlossaryTermProps`) and by `Popover` (line 28, line 30). This is a domain summary type (a strict subset of `GlossaryTerm` from `src/types/glossary.ts`) and is not specific to the React component layer. Living in the component file means it does not appear in `src/types/` and is invisible to a contributor looking for canonical types.
- **Suggested remedy:** Move `GlossaryTermSummary` to `src/types/glossary.ts` alongside `GlossaryTerm`. Replace the local declaration in `InlineGlossaryTerm.tsx` with `import type { GlossaryTermSummary } from "@/types/glossary"`. This also makes the `Pick<GlossaryTerm, ...>` derivation explicit (define `GlossaryTermSummary = Pick<GlossaryTerm, "id" | "term" | "definition">`).

### T-010: Inconsistent type-export style across the codebase

- **Category:** inconsistent-export
- **Severity:** P2
- **Files:** `src/types/lesson.ts:18,3`, `src/types/article.ts:3`, `src/types/glossary.ts:3`, `src/types/quiz.ts:1,10`, `src/types/learningPath.ts:3`, `src/types/database.ts:1,9,20,31,38,46,53,63`, `src/app/[locale]/dashboard/types.ts:3,14,22,32,41,50`, `src/app/[locale]/tools/visit-planner/types.ts:2,3,5,7`, `src/lib/progressExport.ts:3,10`, `src/lib/notifications.ts:3,78`, `src/components/dashboard/AchievementCard.tsx:6`
- **Description:** Type definitions mix `interface` and `type X = {...}` styles with no consistent rule. Examples:
  - `src/types/lesson.ts`: uses `export type LessonListItem = Pick<...>` (line 3) AND `export interface Lesson` (line 18). Mix within the same file.
  - `src/types/database.ts`, `src/types/article.ts`, `src/types/glossary.ts`, `src/types/quiz.ts`, `src/types/learningPath.ts`: pure `export interface` for object types.
  - `src/app/[locale]/dashboard/types.ts`: pure `export type X = {...}` for object types (lines 3, 14, 22, 32, 41, 50). Same shape as `database.ts`-style interfaces but written as type aliases.
  - `src/app/[locale]/tools/visit-planner/types.ts`: mixed — `export type VisitTypeKey = ...` (line 2), `export type StepValue = ...` (line 3), `export type CustomQuestion = {...}` (line 5), `export type PlannerState = {...}` (line 7).
  - `src/lib/progressExport.ts`: `export type QuizScore = {...}` (line 3), `export type ExportedProgress = {...}` (line 10).
  - `src/lib/notifications.ts`: `export type NotificationInput = {...}` (line 3) AND `export interface Notification = {...}` (line 78). Mix within the same file.

  No single rule. Object-shaped types are sometimes `interface`, sometimes `type`. When two structurally-identical types are defined one-as-`interface` and one-as-`type`, contributors must mentally diff them; merging is also blocked (a type alias cannot `extend` an interface in the same direction).

- **Suggested remedy:** Pick one rule for object types. Recommended rule: use `interface` for object-shaped types that can be extended or implemented; use `type` only for unions, intersections, mapped types, primitives, and `Pick`/`Omit` derivations. Apply this rule across `src/types/`, `src/app/[locale]/dashboard/types.ts`, `src/app/[locale]/tools/visit-planner/types.ts`, and `src/lib/notifications.ts`. Codify in the `AGENTS.md` or `src/types/codemap.md`.

### T-011: `any` usage in non-test files

- **Category:** type-leak
- **Severity:** P2
- **Files:** `src/lib/supabase/mockClient.ts:7`, `src/components/dashboard/DashboardSidebar.tsx:35`, `src/components/dashboard/DashboardSidebar.tsx:100`, `src/app/[locale]/learn/LearnClient.tsx:1` (line containing `getCategoryLabel(categoryId as any, locale)`)
- **Description:** Four non-test `any` usages:
  - `mockClient.ts:7`: `set?(name: string, value: string, options?: any): void;` — `MockCookieStore.set` takes untyped options. The real `next/dist/server/web/spec-extension/adapters/request-cookies` `set` method has a concrete `ResponseCookies` `options` type; this `any` hides divergence from the real cookie API.
  - `DashboardSidebar.tsx:35` and `:100`: `t: (key: string, values?: any) => string;` — the `t` (translation) function is hand-typed as accepting `any` for `values`. The real `useTranslations<"dashboard">` return type uses `Record<string, string | number | boolean>` or per-key value maps. The hand-rolled `t` prop type in two internal helper components (`DesktopSidebar`, `MobileBottomNav`) avoids importing the proper next-intl type.
  - `LearnClient.tsx` (per `rg`, line containing `getCategoryLabel(categoryId as any, locale)`): casts `categoryId` to `any` to satisfy `getCategoryLabel`'s parameter type. Hides a real type mismatch — `categoryId` is probably a union-typed value and `getCategoryLabel` expects a wider string.

  Test-file `any` usage (156 hits in `*.test.ts`/`*.test.tsx`) is out of scope for this recon and is generally acceptable.

- **Suggested remedy:**
  - `mockClient.ts:7`: replace `options?: any` with `CookieOptions` from `@supabase/ssr`/`next` or, if the mock genuinely ignores options, type it as `unknown` and have the mock drop it.
  - `DashboardSidebar.tsx`: replace the hand-typed `t: (key: string, values?: any) => string` with `ReturnType<typeof useTranslations<"dashboard">>` (already used in `RecommendedNext.tsx`). Drop the duplicate `t` parameter; pass `t` once via props.
  - `LearnClient.tsx`: investigate the `categoryId as any` cast. Likely `getCategoryLabel` should accept `LessonCategoryId | string` or the call should narrow `categoryId` before passing. Remove the cast.

### T-012: `src/types/codemap.md` declares canonical-type home but `src/types/` omits dashboard, visit-planner, and search types

- **Category:** wrong-location
- **Severity:** P1
- **Files:** `src/types/codemap.md:1-20`, `src/app/[locale]/dashboard/types.ts:1-58`, `src/app/[locale]/tools/visit-planner/types.ts:1-13`, `src/data/searchIndex.en.ts:4-15`, `src/data/searchIndex.es.ts:4-15`, `src/components/mdx/InlineGlossaryTerm.tsx:12`, `src/components/dashboard/AchievementCard.tsx:6`
- **Description:** `src/types/codemap.md` declares `src/types/` to be "TypeScript type definitions for all domain entities and database schema" and lists the canonical files (`content.ts`, `lesson.ts`, `quiz.ts`, `learningPath.ts`, `article.ts`, `glossary.ts`, `database.ts`). However, three categories of domain type live outside this directory:
  - Dashboard types (`Summary`, `LearningPathEntry`, `ActivityItem`, `AchievementItem`, `RecommendedLesson`, `DashboardClientProps`) in `src/app/[locale]/dashboard/types.ts` — see T-005.
  - Visit-planner types (`VisitTypeKey`, `StepValue`, `CustomQuestion`, `PlannerState`) in `src/app/[locale]/tools/visit-planner/types.ts` — see T-006.
  - Search-entry types (`SearchEntry`, `SearchEntryType`) in `src/data/searchIndex.en.ts` and `src/data/searchIndex.es.ts` — see T-003.
    Plus one component-embedded domain type:
  - `GlossaryTermSummary` in `src/components/mdx/InlineGlossaryTerm.tsx` — see T-009.

  The codemap.md self-description is therefore inaccurate: `src/types/` is not the single source of truth. Contributors reading `src/types/codemap.md` have no signal that dashboard, visit-planner, and search types exist elsewhere.

- **Suggested remedy:** Either:
  (a) Move all out-of-place types into `src/types/` (preferred — see T-003, T-005, T-006, T-009) and update `src/types/codemap.md` to list the new files. Or:
  (b) Update `src/types/codemap.md` to explicitly acknowledge the dashboard, visit-planner, and search types and document where they live and why. Less clean but lower-risk.
  Recommend (a).
