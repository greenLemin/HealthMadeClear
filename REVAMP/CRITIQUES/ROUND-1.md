## CRITIC 1 — Staff Engineer

_Focus: Feasibility, hidden complexity, framework/DB behavior, invalid technical assumptions._

### 1. 🔴 Phase 2 (§5.1, §5.2) — `ResetPasswordClient` Breaks Server-Side OTP Confirm Flow

- **Target Section:** Phase 2 — §5.1 Scope (`ResetPasswordClient.tsx`) & §5.2 Step 4.
- **Problem:** Step 4 mandates:
  ```ts
  const search = new URLSearchParams(window.location.search);
  const hash = new URLSearchParams(window.location.hash.replace(/^#/, ""));
  const code = search.get("code") || hash.get("code");
  const token_hash = search.get("token_hash") || hash.get("token_hash");
  const type = search.get("type") || hash.get("type");
  // If code: exchange; else if token_hash: verifyOtp; else: setError(t("errorInvalidResetLink"))
  ```
  In Supabase SSR authentication, password recovery emails typically point to the server route `/[locale]/auth/confirm?token_hash=...&type=recovery&next=/[locale]/auth/reset-password`. The route handler (`confirm/route.ts`) calls `supabase.auth.verifyOtp()` on the server, establishes the session cookies, and redirects the browser to `/[locale]/auth/reset-password`.
  When the browser lands on `reset-password`, `window.location.search` and `hash` contain **no** `code` and **no** `token_hash`. Under the plan's logic, `ResetPasswordClient` will immediately trigger `setError(t("errorInvalidResetLink"))`, completely breaking legitimate recovery flows for all users completing server-verified OTP links.
- **Suggested Fix:** Update `ResetPasswordClient` logic:
  1. Check URL for `code` or `token_hash`. If present, perform client exchange/verification.
  2. If no URL tokens are present, check whether an active session already exists via `supabase.auth.getUser()` or `useAuth()`.
  3. Only if auth state has finished loading and there is _neither_ an active session _nor_ valid URL tokens should `setError(t("errorInvalidResetLink"))` be displayed.

### 2. 🔴 Phase 14 (§17.1, §17.2) — Dynamic Import Code-Splitting Overwritten by Build Scripts

- **Target Section:** Phase 14 — §17.1 Scope & §17.2 Steps 1–4.
- **Problem:** The plan directs replacing `src/data/lessonBundles.ts`, `quizBundles.ts`, `pathBundles.ts`, and `glossaryBundles.ts` with dynamic import loaders. However, all files in `src/data/*Bundles.ts` are auto-generated artifacts produced by `scripts/bundle-lessons.ts`, `scripts/bundle-quizzes.ts`, `scripts/bundle-paths.ts`, and `scripts/bundle-glossary.ts`.
  Line 1 of `src/data/lessonBundles.ts` explicitly states: `// Auto-generated by scripts/bundle-lessons.ts — do not edit by hand.`
  Whenever `npm run content:bundle` or `npm run content:validate` is executed (which Phase 8 mandates during content updates and CI), `scripts/bundle-lessons.ts` will regenerate `lessonBundles.ts` with static imports of both `en` and `es` bundles (`import { lessons as en } from "./lessonBundles.en"`), instantly wiping out the manual code-splitting refactor.
- **Suggested Fix:** Include the generator scripts in Phase 14 scope (`scripts/bundle-lessons.ts`, `scripts/bundle-quizzes.ts`, `scripts/bundle-paths.ts`, `scripts/bundle-glossary.ts`). Update the scripts to stop emitting monolithic combined barrels, and instead generate only the locale-isolated bundle files alongside a dynamic loader utility.

### 3. 🔴 Phase 5 (§8.1, §8.2) — Guest Storage Schema Mismatch Between `AppProviders` and Supabase Migration

- **Target Section:** Phase 5 — §8.1 Scope & §8.2 Step 5 (`guestProgress.ts` / `AppProviders.tsx`).
- **Problem:** The plan states: _"Guest quiz attempts: merge into `STORAGE_KEYS.quizScores` shape used by AppProviders."_
  `AppProviders.tsx` (`STORAGE_KEYS.quizScores`) stores an array of `{ lessonId: string, score: number, passed: boolean }` (using `lessonId`, assuming default max score 100, and omitting user answers).
  In contrast, `guestProgress.ts` (`GuestQuizAttempt`) and Supabase `quiz_attempts` table require `{ quizId: string, score: number, maxScore: number, passed: boolean, answers: number[] }`.
  Merging guest quiz records directly into `STORAGE_KEYS.quizScores` without schema translation discards the `answers` array, loses `maxScore`, and substitutes `lessonId` for `quizId` (e.g. `"reading-nutrition-labels"` instead of `"quiz-reading-nutrition-labels"`). When `migrateGuestProgressToSupabase` subsequently runs upon signup, the payload will either violate foreign key constraints on `quiz_id` or fail Postgres validation.
- **Suggested Fix:** Formally unify the guest quiz type definition in `src/types/progress.ts`. Ensure `localStorage` key `hmc-quiz-scores` preserves `quizId`, `lessonId`, `score`, `maxScore`, `passed`, and `answers`. Update both `AppProviders.tsx` and `guestProgress.ts` to consume and write this unified shape.

### 4. 🟡 Phase 1 (§4.3) — UUID Tiebreaker in Quiz Deduplication Query

- **Target Section:** Phase 1 — §4.3 Step B (`015_quiz_attempts_best_score.sql`).
- **Problem:** The deduplication SQL uses `OR (a.score = b.score AND a.attempted_at = b.attempted_at AND a.id < b.id)`. In this schema, `id` is a random UUID (`gen_random_uuid()`). While UUID comparison (`<`) is deterministic in Postgres, it is an arbitrary lexicographical comparison, not a temporal sequence.
- **Suggested Fix:** Acceptable as an arbitrary tiebreaker, but add a code comment in the SQL file clarifying that UUID comparison is strictly for deterministic tiebreaking when timestamp and score are identical.

### 5. 🟡 Phase 10 (§13.1) — Root `not-found.tsx` Layout Isolation in Next.js 16 App Router

- **Target Section:** Phase 10 — §13.1 (`src/app/not-found.tsx`).
- **Problem:** Root `src/app/not-found.tsx` does not inherit `[locale]/layout.tsx`. The plan correctly notes importing `globals.css` and font variables, but in Next.js 16 App Router, root `not-found.tsx` requires explicit `<html>` and `<body>` tags with `suppressHydrationWarning` if theme classes are applied dynamically by inline scripts (`pref-bootstrap.js`).
- **Suggested Fix:** Ensure `src/app/not-found.tsx` renders static theme tokens (`theme-light`) without depending on client-side cookie reads to avoid hydration mismatches on uncaught 404 routes.

## CRITIC 2 — Security Engineer

_Focus: RLS, injection, authentication bypass, data privacy, PII/PHI leakage._

### 1. 🔴 Phase 3 (§6.1, §6.3) — Missing Server-Side Protection on `/api/contact` After RLS Lockdown

- **Target Section:** Phase 3 — §6.1 & §6.3 (`src/app/api/contact/route.ts` & `ContactClient.tsx`).
- **Problem:** Phase 1 drops the public INSERT policy from `contact_submissions`, channeling all submissions through `/api/contact` using the privileged `SUPABASE_SERVICE_ROLE_KEY`.
  However, Phase 3 relies solely on a client-side button lock (`inFlight` ref in `ContactClient.tsx`) to prevent double submits, treating API idempotency as "optional."
  Because `/api/contact` operates with service-role permissions that bypass Postgres RLS, any script or bot can send HTTP POST requests directly to `/api/contact`, completely ignoring the client button lock. Without mandatory server-side rate limiting, origin verification, and honeypot validation, the endpoint is vulnerable to spam flooding, database resource exhaustion, and automated PII injection.
- **Suggested Fix:** Phase 3 MUST require in `src/app/api/contact/route.ts`:
  1. Origin / Referer validation against the allowed site hostname.
  2. Server-side IP rate limiting using `checkRateLimitDistributed` (falling back to memory sliding window).
  3. Server-side rejection of submissions containing filled honeypot fields (`hp_company` or `website`).
  4. Payload size limits (max 10KB JSON body) and strict email regex validation.

### 2. 🟡 Phase 1 (§4.3) — Unconstrained User Metadata in `handle_new_user` Trigger

- **Target Section:** Phase 1 — §4.3 Step A.3 (`014_launch_reconcile.sql`).
- **Problem:** `handle_new_user()` inserts `new.raw_user_meta_data->>'display_name'` directly into `public.profiles.display_name`. An attacker during signup can supply a multi-megabyte string or malicious unicode sequences in `raw_user_meta_data`, leading to profile bloat or log injection when rendered in telemetry or dashboard components.
- **Suggested Fix:** Truncate and sanitize the display name in the PL/pgSQL function:
  ```sql
  insert into public.profiles (id, display_name)
  values (new.id, substring(trim(coalesce(new.raw_user_meta_data->>'display_name', '')) from 1 for 100));
  ```

### 3. 🟡 Phase 16 (§19.1) — Incomplete Sentry PII / PHI Breadcrumb Scrubbing

- **Target Section:** Phase 16 — §19.1 (`src/lib/errorReporting.ts`).
- **Problem:** Scrubbing only `event.extra` and `breadcrumbs[].data` for keys `lesson, quiz, path, email` misses health-adjacent information embedded in URL paths (e.g. `/glossary/hypertension`, `/tools/care-guide?symptom=fever`), search query parameters (`?q=insulin`), and form inputs captured by default Sentry DOM breadcrumbs.
- **Suggested Fix:** In `errorReporting.ts`, configure Sentry's `beforeSend` and `beforeBreadcrumb` hooks to strip query parameters from URL strings, redact input values from DOM interaction breadcrumbs, and strip search terms matching health topics.

### 4. 🟡 Phase 3 (§6.2) — Google Analytics Search Term Tracking vs Privacy Disclosure

- **Target Section:** Phase 3 — §6.2 (`privacy.collectBodyAnalytics`).
- **Problem:** The privacy copy states that GA collects page URLs including lesson and article slugs. If user search queries (e.g., search modal queries for personal conditions) are appended to URLs or tracked via GA custom events (`trackEvent`), this transmits health search intent to Google.
- **Suggested Fix:** Explicitly verify in `src/lib/analytics.ts` and `SearchDialog.tsx` that search query text is never passed as a URL search param or custom GA event parameter, and ensure IP anonymization (`anonymize_ip: true`) is enforced in the GA tag configuration.

## CRITIC 3 — UX Lead

_Focus: Visual audit fidelity, mobile ergonomics, design system polish, perceived quality._

### 1. 🔴 Phase 11 (§14.1) — Critical Tap Target Violations Omitted from Scope

- **Target Section:** Phase 11 — §14.1 Scope (`Touch targets, glossary A-Z, inline terms`).
- **Problem:** `AUDIT-VISUAL.md` highlighted widespread mobile touch target failures (< 44×44px). While Phase 11 addresses Footer links, Glossary A-Z, and Checklist rows, it omits several high-frequency interaction points:
  1. **Breadcrumbs:** Breadcrumb links on Lesson, Article, and Path pages render as small inline text (`~18px` height), causing mis-taps on mobile.
  2. **Mobile Drawer Close Control:** The mobile navigation drawer close button (`Header.tsx`) renders at `36×36px`.
  3. **Quiz Option Rows:** Quiz answer choices on mobile 390px are tightly packed with minimal padding, making single-option selection error-prone for users with motor impairments.
  4. **Category Filter Pills:** In `LearnClient.tsx`, category pills ("All", "Medications", etc.) have tight vertical padding (`py-1`).
- **Suggested Fix:** Expand Phase 11 scope to include:
  - Breadcrumbs: `min-h-[44px] py-2.5 inline-flex items-center`.
  - Drawer close button in `Header.tsx`: enforce `min-h-[44px] min-w-[44px] p-2.5`.
  - Quiz option containers (`QuizOption.tsx`): `min-h-[48px] p-4 gap-3 rounded-2xl`.
  - Learn category pills: `px-4 py-2.5 min-h-[44px]`.

### 2. 🟡 Phase 13 (§16.1) — Hero Clutter and CTA Pushdown on Mobile 390px

- **Target Section:** Phase 13 — §16.1 (`Hero.tsx`).
- **Problem:** On 390px viewports, adding the new `TrustBanner` (Phase 8) directly above the Hero H1, combined with the hero badge, subtitle, and media preview, pushes the primary CTAs ("Start Learning" / "Explore Tools") below the fold (`> 844px`). Reducing the desktop H1 clamp does not solve mobile vertical space exhaustion.
- **Suggested Fix:** On mobile viewports (`< 640px`):
  - Condense `TrustBanner` to a single line with `text-label-sm` and compact padding (`py-1 px-3`).
  - Move the autoplay video preview below the CTA buttons in the DOM/layout flow so the two primary action buttons appear within the initial screen view.

### 3. 🟡 Phase 12 (§15.1) — Search Modal Mobile Keyboard Overlap & Screen Reader Churn

- **Target Section:** Phase 12 — §15.1 (`SearchDialogContent.tsx`).
- **Problem:** On mobile devices, the virtual keyboard consumes ~300px of height. Grouping search results into 5 distinct categories with section headers (`Lessons`, `Paths`, `Articles`, `Glossary`, `Tools`) forces results off-screen. Furthermore, updating `aria-live="polite"` on every keystroke without a debounce causes screen readers to stutter result counts continuously.
- **Suggested Fix:**
  - Debounce the `aria-live` announcement by 350ms so it speaks only after user pauses typing.
  - Constrain search modal content to `max-h-[calc(100dvh-14rem)]` with smooth scrolling so the input and top results remain visible above the virtual keyboard.

## CRITIC 4 — Clinical Content Reviewer (PharmD Persona)

_Focus: Medical accuracy, health literacy (plain language), disclaimers, triage liability._

### 1. 🔴 Phase 4 (§7.1, §7.2) — Unchecked Triage Guidance in Care Guide Scenarios

- **Target Section:** Phase 4 — §7.1 & §7.2 (`CareGuideClient.tsx` and `src/messages/{en,es}.json`).
- **Problem:** The plan addresses `tools.homeCareBody` and the "sore throat" scenario. However, the care guide message catalog (`tools.scenarios.*`) includes multiple scenarios (e.g. fever, sprains, mild burns, missed medication doses) where copy currently provides symptom-specific advice on whether to visit urgent care versus waiting at home.
  Providing symptom-specific guidance without clinical history, vital signs, or medication reconciliation constitutes medical triage advice and presents substantial liability if a patient with atypical presentation (e.g., atypical cardiac symptoms) delays emergency care based on a scenario description.
- **Suggested Fix:** Phase 4 scope MUST mandate an exhaustive review of ALL scenario keys in `tools.scenarios.*` in both `en.json` and `es.json`.
  Every scenario must be standardized to an educational comparison format:
  1. "How clinicians evaluate [symptom] in different settings."
  2. Explicit inclusion of warning signs requiring immediate emergency evaluation.
  3. Mandatory persistent disclaimer: _"This scenario illustrates common care settings and is not a clinical recommendation for your symptoms."_

---

### 2. 🔴 Phase 8 (§11.1, §11.2) — Content Validator Allows Dummy Citations and Outdated Clinical Content

- **Target Section:** Phase 8 — §11.1 Scope & §11.2 (`scripts/validate-content.ts`).
- **Problem:** The proposed `validate-content.ts` check only asserts `sources.length >= 1` and `reviewedBy` is a non-empty string.
  This allows placeholder strings (e.g. `reviewedBy: "Medical Team"`, `sources: ["Web"]`) to pass CI build gates. In addition, it fails to validate `lastReviewed` date currency (clinical guidelines recommend review within 24 months) or verify that citations reference recognized authoritative bodies (e.g., FDA, CDC, NIH, MedlinePlus, USP).
- **Suggested Fix:** In `scripts/validate-content.ts`:
  1. Enforce that `reviewedBy` contains a valid clinical credential or recognized institutional board (e.g. regex matching `/(MD|DO|PharmD|RN|MSN|MPH|Clinical Advisory Board)/i`).
  2. Enforce that `lastReviewed` is a valid ISO date `YYYY-MM-DD` dated within the past 24 months.
  3. Enforce that `sources` entries are non-empty strings with at least 5 characters matching recognized health institutions.

---

### 3. 🟡 Phase 4 & Phase 8 — Spanish Medical Terminology and Plain-Language Accuracy

- **Target Section:** Phase 4 (§7.1) & Phase 8 (§11.1).
- **Problem:** Literal translation of medical idioms in `es.json` risks comprehension failure for low-health-literacy Spanish speakers (e.g. translating "over-the-counter" as "sobre el mostrador" instead of "medicamentos de venta libre", or "urgent care" as "cuidado urgente" instead of "centro de urgencias médicas").
- **Suggested Fix:** Mandate that all updated Spanish strings for care guide scenarios, disclaimers, and trust banners be cross-referenced with NIH/MedlinePlus en español plain-language standards.

---

### 4. 🟡 Phase 12 (§15.1, §15.2) — Visit Planner Question Framing & Consultation Time Constraints

- **Target Section:** Phase 12 — §15.1 & §15.2 (`useVisitPlanner.ts`).
- **Problem:** The average primary care visit lasts 15–18 minutes. If the visit planner's default selected questions are overly broad, patients may overwhelm the encounter and miss critical safety questions (e.g., medication reconciliation, red flag symptoms, follow-up instructions).
- **Suggested Fix:** Ensure default pre-selected question IDs (`new-symptom:0`, `medication:0`) map to high-value safety questions:
  1. _"What is the main goal of this treatment?"_
  2. _"What side effects or warning signs should prompt me to call your office?"_
  3. _"When and how should I follow up?"_

## CRITIC 5 — Ruthless Project Manager

_Focus: 4-day feasibility, phase ordering, deployment deadlocks, merge safety, rollback plans._

### 1. 🔴 Calendar / Phase 1 vs Phase 6 — Production Retake Outage Deadlock

- **Target Section:** Phase 1 (§4.1), Phase 6 (§9.1, §9.5), Section 3 Calendar.
- **Problem:**
  - **Day 1** deploys Phase 1 (DB migration `015_quiz_attempts_best_score.sql` adding `UNIQUE(user_id, quiz_id)`).
  - **Day 2** deploys Phase 6 (updating the client code from `.insert()` to `.upsert()`).

  If Phase 1 is executed against the live production database on Day 1, any signed-in user who retakes a quiz before Phase 6 merges on Day 2 will trigger `supabase.from("quiz_attempts").insert(...)`. This will immediately crash with Postgres error `23505 (unique_violation)`.
  The plan creates a 24-hour window where existing production functionality is actively broken!

- **Suggested Fix:** Couple Phase 1 SQL `015` and Phase 6 client code into an **Atomic Release Gate**:
  - Migration `014` (RLS, functions, indexes) can safely deploy on Day 1.
  - Migration `015` (deduping + unique constraint) MUST NOT be applied to the production database until the Phase 6 client PR is merged and deployed to Netlify.

**UX 🔴 quiz options / drawer close / learn pills omitted — MOSTLY STALE.**
