### 1. 🔴 Phase 9 (§12.1), `src/middleware.ts` & `src/lib/supabase/middleware.ts` — `updateSession` Strips `next-intl` Headers and Cookies During `@supabase/ssr` `setAll` Re-instantiation

- **Target Section:** Phase 9 — §12.1 Scope (`src/lib/supabase/middleware.ts`) & Global Constraints (§3 / §4).
- **Problem:**
  In `src/middleware.ts`:

  ```ts
  const handleI18n = createMiddleware(routing);
  export default async function middleware(request: NextRequest) {
    const response = handleI18n(request);
    return await updateSession(request, response);
  }
  ```

  When `updateSession(request, response)` is called, `supabaseResponse` is initially initialized to `response`.
  However, in `src/lib/supabase/middleware.ts` (lines 68–71):

  ```ts
  setAll(cookiesToSet) {
    // ...
    supabaseResponse = NextResponse.next({ request });
    cookiesToSet.forEach(({ name, value, options }) =>
      supabaseResponse.cookies.set(name, value, options)
    );
  }
  ```

  `NextResponse.next({ request })` instantiates a **brand new, empty response**.
  If `@supabase/ssr` refreshes or mutates auth tokens during `getUser()`, executing `supabaseResponse = NextResponse.next({ request })` **completely discards the incoming `response`** generated by `handleI18n(request)`.
  This strips:
  1. `next-intl` internal rewrite headers (`x-next-intl-locale`, `x-middleware-rewrite`).
  2. Locale cookies (`NEXT_LOCALE`) set when switching languages.
  3. Any 307/308 locale redirection responses returned by `handleI18n(request)` when visiting the bare root path `/`.

- **Suggested Fix:**
  In `src/lib/supabase/middleware.ts`:
  1. Early-return if `response` is already a redirection from `handleI18n` (status 300–399):
     ```ts
     if (response && response.status >= 300 && response.status < 400) {
       return response;
     }
     ```
  2. When re-instantiating `supabaseResponse` in `setAll`, preserve and copy all headers and pre-existing cookies from the incoming `response`:
     ```ts
     setAll(cookiesToSet) {
       cookiesToSet.forEach(({ name, value }) =>
         request.cookies.set(name, value)
       );
       const prevHeaders = new Headers(supabaseResponse.headers);
       const prevCookies = supabaseResponse.cookies.getAll();
       supabaseResponse = NextResponse.next({ request, headers: prevHeaders });
       prevCookies.forEach((cookie) => supabaseResponse.cookies.set(cookie));
       cookiesToSet.forEach(({ name, value, options }) =>
         supabaseResponse.cookies.set(name, value, options)
       );
     }
     ```

### 2. 🟡 Phase 5 (§8.1) / Phase 6 (§9.1) — `AppProviders.recordQuizScore` Overwrites Higher Scores on Retakes in Local State

- **Target Section:** Phase 5 — §8.1 Scope (`AppProviders.tsx`) & Phase 6 — §9.1 (`mutations.ts`).
- **Problem:**
  Phase 6 (§9.1) correctly instructs `mutations.ts` to skip writing to Supabase when a user's retake score is lower than their existing score (`if (existing && score <= existing.score) skip write`).
  However, in `AppProviders.tsx`, `recordQuizScore(lessonId, score, passed)` unconditionally overwrites `STORAGE_KEYS.quizScores` in React state and `localStorage` with the latest attempt.
  If a user scores 100% (5/5) on attempt 1, and later retakes the quiz for practice and scores 60% (3/5), their client UI (and subsequent guest sync) downgrades the local best score to 60%.
- **Suggested Fix:**
  In `AppProviders.tsx`, update `recordQuizScore`:
  ```ts
  const recordQuizScore = useCallback((lessonId: string, score: number, passed: boolean) => {
    setQuizScores((prev) => {
      const existing = prev[lessonId];
      if (existing && existing.score > score) {
        return prev; // Preserve best score
      }
      return {
        ...prev,
        [lessonId]: { lessonId, score, passed, completedAt: new Date().toISOString() },
      };
    });
  }, []);
  ```

## CRITIC 2 — Security Engineer

_Focus: RLS, auth, injection, privacy of health-adjacent data, rate limiting._

### 1. 🔴 Phase 9 (§12.1) & `AuthProvider.signOut` — Network Rejection During SignOut Leaves Valid Auth JWT in `document.cookie` on Public Kiosks

- **Target Section:** Phase 9 — §12.1 Scope (`src/components/providers/AuthProvider.tsx`) & Phase 5 (§8.1).
- **Problem:**
  Phase 9 specifies:
  ```ts
  try {
    await supabase.auth.signOut();
  } catch {
    /* ignore */
  } finally {
    resetLocalProgress();
    router.push("/");
  }
  ```
  If `supabase.auth.signOut()` throws a network error (e.g. offline, timeout, GoTrue endpoint 502/503), `@supabase/ssr` client-side cookie teardown is skipped.
  While `resetLocalProgress()` clears `localStorage` health keys, the unexpired Supabase JWT cookie (`sb-*-auth-token`) remains in `document.cookie`.
  When the next user at a public health kiosk or library clicks "Dashboard" or navigates back, `src/lib/supabase/middleware.ts` reads the valid JWT cookie and automatically grants access to the previous user's account without requiring credentials.
- **Suggested Fix:**
  In `src/lib/clearLocalHealthData.ts`, export an explicit client cookie expiration utility:
  ```ts
  export function expireClientAuthCookies(): void {
    if (typeof document === "undefined") return;
    const cookies = document.cookie.split(";");
    for (const cookie of cookies) {
      const name = cookie.split("=")[0]?.trim();
      if (name && /^sb-.*-auth-token/.test(name)) {
        document.cookie = `${name}=; Max-Age=0; path=/; SameSite=Lax`;
      }
    }
  }
  ```
  In `AuthProvider.tsx`, invoke `expireClientAuthCookies()` inside the `finally` block of `signOut()`.

### 2. 🟡 Phase 1 (§4.3 Step A.2) & `014_launch_reconcile.sql` — Explicit Cascade Verification for `delete_user` RPC

- **Target Section:** Phase 1 — §4.3 Step A.2 (`014_launch_reconcile.sql`).
- **Problem:**
  `delete_user` executes `DELETE FROM auth.users WHERE id = auth.uid()`. If any foreign key referencing `auth.users(id)` lacks `ON DELETE CASCADE` (or if a newly added table adds a restricting reference), the RPC fails with Postgres error `23503` (foreign_key_violation), preventing user deletion.
- **Suggested Fix:**
  In `014_launch_reconcile.sql`, explicitly audit and add `ON DELETE CASCADE` to all table constraints referencing `auth.users(id)` (`profiles`, `lesson_progress`, `quiz_attempts`, `streaks`, `daily_log`, `notifications`).

### 3. 🟡 Phase 3 (§6.1.1) & `src/lib/rateLimitDistributed.ts` — In-Memory Rate Limit Map Unbounded Growth Guard

- **Target Section:** Phase 3 — §6.1.1 & `src/lib/rateLimitDistributed.ts`.
- **Problem:**
  The fallback in-memory rate limiter stores IP strings. Under an IP-rotation flood attack targeting `/api/contact`, the Map could grow continuously if timestamps are only purged on active lookups.
- **Suggested Fix:**
  Ensure the memory rate limit bucket uses an LRU cache or capped Map (max 5,000 entries) with automatic LRU eviction.

## CRITIC 3 — UX Lead

_Focus: Visual polish, mobile responsive behavior, typography, touch targets, state transitions._

### 1. 🔴 Phase 10 (§13.1) & `Header.tsx` — Mobile Navigation Accordion Trapping & Vertical Viewport Overflow on Tablet/Landscape

- **Target Section:** Phase 10 — §13.1 Scope (`src/components/Header.tsx`).
- **Problem:**
  Phase 10 specifies that for `< xl` (viewports `< 1280px`, including iPad 768px/1024px and mobile devices in landscape), the navigation renders as a full-width accordion underneath the sticky header bar.
  The expanded navigation menu includes:
  - 8 primary navigation links (`Learn`, `Paths`, `Articles`, `Tools`, `Glossary`, `About`, `Accessibility`, `Contact`)
  - Language toggle (`EN` / `ES`)
  - Display controls (`Text Size`, `Contrast`)
  - Auth CTA buttons (`Sign In`, `Get Started`)

  The total expanded height exceeds **550px**.
  Because `Header.tsx` is fixed/sticky (`sticky top-0 z-50`), if the expanded menu container lacks `max-h` and scrolling constraints, the bottom items (`Glossary`, `About`, `Contact`, `Sign In`) extend past the bottom of the viewport on tablet landscape (e.g. 768×1024 rotated to 1024×768) or smaller mobile screens. The user cannot scroll the accordion because touch events scroll the underlying locked background page.

- **Suggested Fix:**
  In `src/components/Header.tsx`, apply scroll constraints to the mobile menu accordion wrapper:
  ```tsx
  <div className="max-h-[calc(100dvh-4rem)] overflow-y-auto overscroll-contain border-t border-outline/10 bg-surface px-4 py-6 shadow-elevation-3">
    {/* Navigation items, utilities, and auth buttons */}
  </div>
  ```

### 1. 🔴 Phase 15 (§18.1) & Mini-Spec §10.3 — Printed Lesson & Article Sheets Omit Clinical Medical Disclaimers

- **Target Section:** Phase 15 — §18.1 Scope & Mini-Spec §10.3 Print CTA Spec.
- **Problem:**
  Phase 15 implements print CTAs (`window.print()`) on lesson pages (`/learn/[slug]`) and article pages (`/articles/[slug]`).
  In `@media print`, `globals.css` applies `.no-print` to the global header, navigation, and site footer.
  While Phase 15 explicitly mandates a print-only educational footer on the Care Guide tool (`CareGuideClient.tsx`), it does **not** specify this footer for lessons or articles.
  In high-risk medication lessons such as `understanding-prescription-labels`, `pain-medications-safely`, and `asking-about-medications`, patients frequently print these educational summaries to take to medical appointments or post on medicine cabinets.
  Without an explicit print-only disclaimer on the printed paper, the educational sheet appears as a standalone clinical guideline without warnings to consult a prescribing doctor or pharmacist for individualized dosing, creating severe clinical liability.
- **Suggested Fix:**
  In `LessonPageClient.tsx` and `ArticlePageClient.tsx`, add a dedicated print-only clinical disclaimer block:
  ```tsx
  <div className="hidden print:block mt-8 pt-4 border-t border-outline/30 text-body-sm text-on-surface-variant">
    <p>{t("disclaimer.printMedicalWarning")}</p>
    <p className="mt-1 text-label-sm">
      {t("disclaimer.printTimestamp", { date: new Date().toLocaleDateString() })}
    </p>
  </div>
  ```
  **Required Copy (both locales):**
  - **EN:** _"Health Made Clear is for educational purposes only and does not provide medical or pharmaceutical advice. Always consult your doctor or pharmacist about your specific prescriptions and health conditions."_
  - **ES:** _"Health Made Clear es únicamente para fines educativos y no proporciona asesoramiento médico ni farmacéutico. Consulte siempre a su médico o farmacéutico sobre sus recetas y condiciones de salud específicas."_

### 2. 🟡 Phase 4 (§7.2) — Plain-Language Reading Level for Atypical ACS Warning Signs

- **Target Section:** Phase 4 — §7.2 (`scenarioChestPainBody` EN & ES).
- **Problem:**
  The proposed text in §7.2 includes a complex multi-clause sentence: _"including when there is no crushing chest pain (this is more often how heart attacks present in women, older adults, and people with diabetes)"_.
  In low-health-literacy populations experiencing acute stress, parenthetical qualifiers hinder rapid comprehension of life-threatening warning signs.
- **Suggested Fix:**
  Split into two distinct, high-clarity sentences:
  _"Heart attacks do not always cause crushing chest pain. In women, older adults, and people with diabetes, warning signs often include jaw, neck, back, or arm pain, sudden shortness of breath, unexplained cold sweats, nausea, or dizziness. If you notice these symptoms, do not wait and do not self-treat. In the United States, call 911 immediately."_

**Sec 🔴 1 as stated — “`signOut` throw skips `@supabase/ssr` cookie teardown” — OVERSTATED.**

**Reject** “throw ⇒ cookies always remain / setAll never runs.” **Accept** the kiosk hole that is actually open (CF-44): throw **before** `_removeSession`; `sessionError` early-return **without** remove; v7 `finally` wipes storage not cookies; middleware expire-on-`error` does **not** run when leftover JWT is still **valid**.

**CF-43 — C53 `setAll` rebuilds `NextResponse.next()` ∪ `handleI18n` rewrite/307 ∪ CF-38 cookie copy only on dashboard 307 ∪ tests that never invoke `setAll` after an i18n response.**
